# Execute an authorized slice

**Enter when:** implementation is requested for a reviewed slice with actionable tracker handoffs. For a focused direct code change without a ticketed slice, follow design's fidelity procedure and project implementation rules; do not invent tickets solely to enter this playbook.

**Read:** slice parent, selected task and prerequisites, exact accepted target/review, affected design-map entries and project checks; [delegation](../references/delegation.md), [preserve settled decisions](../principles/preserve-settled-decisions.md), and [proportionate evidence](../principles/proportionate-evidence.md). Resolve actual project execution policy through [project bindings](../references/project-bindings.md).

## Deliver the slice

1. Establish one acceptance bar in the existing task or [worker brief](../assets/worker-brief-template.md): caller-visible behavior and failures, production capability exercised, supplied external dependencies, exact checks and what they establish, mandatory project gates, any necessary live question/cases/run limit, and the stop/escalation condition. Reuse accepted scope and existing records; create no parallel verification document. Missing details normally come from source and project instructions rather than another approval round.
2. Assign ownership and the tracker claim. Default to a fresh independent worker per ticket to preserve context capacity; the coordinator may choose reuse or local execution when the task and current context make that better, within project policy. Give exact task/shared-context paths, writable ownership, selected principle paths, and the acceptance bar. Tell workers they are not alone and must preserve others' edits. Without a recorded concurrency policy, use one worker at a time. If delegation is unavailable, report the limitation and continue permitted local work without claiming a required fresh-worker policy was met.
3. Resolve the caller's contract before filling in implementation. Exercise the production capability with real internal composition and controlled external dependencies. Add protocol or real local-runtime checks for distinct adapter, persistence, cancellation, or lifecycle risks. If provider feasibility is unknown, probe the disputed real mechanism early with a bounded experiment. Live quality evaluation is a separate claim, not the default implementation loop.
4. Inspect the returned diff, consequential behavior, evidence, and task status before integration or dependent work. Reuse valid check results for unchanged relevant code, configuration, dependencies, and inputs. Rerun for meaningful changes, failed checks, unexplained results, or an unproven composition risk; a coordinator or fresh reviewer does not automatically repeat the worker's suite. Respect hooks and commit policy without stashing, rewriting, or staging unrelated work.
5. Maintain affected module/review coverage, supported imports, important states, accepted-target records, and qualifying design decisions. Use [design](design.md) for required matched fidelity checks. Keep settled direction; return material scope changes to [planning](planning.md). Run the exact completion checks and mandatory project gates, then demonstrate the operable slice against its accepted target.
6. Stop implementation verification when the stated bar passes. Add no check, gate, sign-off, or review round merely because more checking is possible. A new consequential defect, unmet requirement, changed composition, or explicit scope decision can justify a documented revision to the bar; existing mandatory gates still apply. Respect live-evaluation limits and report any remaining gap rather than enlarging the matrix or calling an inconclusive result a pass. Report pre-existing failures separately from regressions and follow project policy for blockers.
7. Present the integrated result for required human review. Implementation completion does not establish acceptance. Refine feedback within scope; close the slice only when required work, record updates, and actual user acceptance are satisfied.

**Deliver:** outcome and task/artifact links, real/simulated boundaries, and exact checks and limits. Report implementation completion, verified behavior and human acceptance separately under the [review contract](../references/review-contract.md), with pending acceptance or next actionable work explicit. Do not infer acceptance from worker completion or passing tests.
