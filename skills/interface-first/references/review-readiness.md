# Make the assigned UI review operable

Use this reference for missing UI review prerequisites or an explicitly assigned UI foundation. General workspace setup stays with the caller. Inspect existing conventions and fill only gaps relevant to the requested surface; a focused review does not require rebuilding the whole catalog.

1. Resolve the affected actual components/styles/compositions, owning design entries, accepted targets and existing launch/review tools through [project bindings](project-bindings.md). Try the available entries and record observed readiness, controlled dependencies, fixtures and reset paths. Use tool-specific skills for mechanics when available, without installing a new platform by implication.
2. Establish usable module/state/review links under the [UI contract](workflow-contract.md). A named renderable element needs clear ownership, a small semantic interface and runnable coverage of its production implementation; states/variants live within those scenarios. Preserve supported imports and keep fixtures/simulations outside production interfaces and outputs. Apply project directory/colocation conventions without an unrelated migration.
3. Reconcile the affected map, targets and known rationale through [design records](design-records.md). If the project lacks a map, use a proportionate entry linked from existing project guidance; the [design-map template](../assets/design-map-template.md) supports a requested broad foundation. A broad foundation covers the supported named interface, relationships, source, owners, important states and review discovery; an individual review maintains its affected entries. Preserve one discovery route and exact approval provenance, without inventing history.
4. Operate representative affected production paths and important controlled states, including parent context and a matched deliberate variation when comparison readiness is the assignment. Run relevant checks for actual source changes; retain real/simulated and verification limits. Return usable entries, record/coverage changes and concrete remaining gaps to the calling procedure. Substantial missing preparation becomes caller-owned planning/execution work; report the unmet prerequisite instead of claiming readiness or creating tasks here.

Assessment-only authorization returns findings. Authorized preparation may repair the assigned prerequisites. Neither authorizes a whole-project setup, tracker mutation or new architecture by itself.
