# Execute authorized work

**Enter when:** implementation or repair is authorized, either as ticketed slices or a direct change. Use existing scope and settled decisions. Do not invent tickets to execute; if a material decision remains, resolve that part through [planning](planning.md) while continuing independent work.

**Read:** project instructions, accepted contracts/targets and decisions, current code, relevant evidence, task/prerequisites when present and required project checks. Use [coordination](../references/coordination.md) for permitted delegation and [skill routing](../references/skill-routing.md) for expertise.

## Implement, integrate and finish

1. Establish the completion bar in the existing task/record or concise assignment: observable behavior and failures, production capability, supplied dependencies, focused checks and their distinct claims, mandatory gates, necessary bounded live question/cases/run limit, stop conditions and any actual human acceptance requirement. The [worker brief](../assets/worker-brief-template.md) is optional, useful for a fresh executor. Resolve routine details from code and project instructions; reuse covered approval.
2. Own the direct change or assign bounded work only when permitted. Preserve unrelated edits and follow project claim/commit policies. Carry exact decisions, authorization, paths and completion evidence across assignments. No model, worker freshness or concurrency policy is imposed here; local execution is valid.
3. Resolve the caller-visible contract before filling in implementation. Reuse actual capabilities and supported composition; keep invariants and lifetime ownership intact. Exercise real internal composition with controlled external dependencies. Add protocol/local-runtime evidence for consequential adapter, persistence, cancellation or lifecycle risks; if feasibility is disputed, test the disputed mechanism early with a bounded experiment. Simulation and live quality evaluation establish different claims.
4. When UI fidelity needs assessment, discover/read `interface-first`. Supply the changed running source/revision, exact accepted target and approval scope, affected states/consumers, operating instructions, known simulations and report-only versus permitted repair scope. Expect matched fidelity findings or scoped refinements, source/artifact references, evidence/limits, actual decision/acceptance state and remaining deviations. It may repair authorized UI differences; consequential new design choices return as decisions, not silently accepted targets.
5. **Resume integration after the specialist result.** Inspect actual changes and evidence, reconcile findings with the original scope, and complete remaining production wiring, affected-consumer checks, owning-record updates and tracker state when applicable. Preserve Interface First's UI review/target requirements without treating its demonstration as proof of backend capability or overall completion. Required record reconciliation precedes dependent work. Verify returned worker/specialist results rather than accepting a confident report alone.
6. Run the stated completion checks and mandatory gates. Reuse valid results for unchanged relevant source, configuration, dependencies and inputs; rerun for meaningful changes, failures, unexplained results or an unproven composition risk. A new consequential defect, unmet requirement or changed scope can justify revising the bar; a new executor alone cannot. Stop when it passes; honor bounded live limits and report inconclusive checks accurately. Separate pre-existing failures from regressions.
7. Deliver the integrated result against the original outcome. Obtain human acceptance only where the request/project requires it; do not invent a sign-off. Distinguish implementation complete, verified behavior, design approval and actual human acceptance. Pending acceptance is pending, not implied by tests or silence. Continue covered feedback; stop only at completion, a genuine blocker or a required unresolved decision.

**Deliver:** actual integrated outcome, source/task/artifact links, checks and claims/limits, real/simulated boundaries, record status and any remaining acceptance or next action. A specialist result or completed ticket is intermediate when broader work remains authorized.
