# Turn scoped work into actionable tasks

**Enter when:** the user requests tracker tasks for an existing plan, reviewed outcome or preparation work. This playbook creates tasks; it starts no implementation or worker dispatch.

**Read:** selected scope, existing tracker records, actual decision/approval state, dependencies and relevant specialist results. Resolve the project's task backend and its tool/skill through actual discovery; follow its hierarchy, claim and readback conventions.

## Create and verify

1. Inspect existing records and extend them rather than duplicating work. Recover IDs, hierarchy and actual dependencies. Resolve material scope gaps through [planning](planning.md); missing historical rationale alone is not a reason to reopen settled decisions.
2. Put shared outcome, scope/exclusions, accepted decisions, baseline/target references, capability/simulation boundaries, constraints and integrated completion evidence in the existing parent or equivalent. Use a parent only when the project's hierarchy and work warrant one; an epic is not universal.
3. Split by coherent result, ownership, prerequisites or distinct risk. A tiny change may need one task. Each actionable handoff has its result, affected files/capability, ownership, genuine dependencies, completion predicate, focused checks/claims, mandatory gates, supplied dependencies, necessary bounded live evidence and stop/escalation conditions. Hierarchy and scheduling order do not establish dependency edges.
4. Carry specialist results into applicable criteria. For UI, use Interface First's exact reviewed source/target, approved units/states, simulations, module/review coverage, affected consumers and owning-record updates. If an unresolved UI question blocks a handoff, invoke `interface-first` through [skill routing](../references/skill-routing.md) with that question and scope, then resume task creation using its actual result/limits. Do not rerun design to ticket an accepted result. Explicitly assign stale-target or rationale reconciliation before dependent changes, within one task when one owner can do both; disclose records still awaiting repair.
5. Assign integration, verification and any human checkpoint required by the actual project/outcome. A prerequisite user decision stays visible and ends the dependent scope until resolved; task creation does not grant implementation authority.
6. Create parents before children where required. Retain returned IDs and read back stored content, hierarchy, prerequisites, owner/executor and exact evidence/design links. Report the first actionable task and any backend limits. One writer owns tracker mutations; use [coordination](../references/coordination.md) only if delegation is permitted and useful. Keep tracker work as execution truth; create no duplicate `tasks.md`.

**Deliver:** task links/IDs, verified hierarchy and dependencies, first actionable work, pending decisions and readback limits. An authorized ticketing request needs no second hierarchy approval. Continue to [execution](execute.md) only when execution is also authorized.
