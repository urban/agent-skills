# Review how the work was done

Use actual development evidence: conversation, task/session records, tool results, diffs, checks, handoffs, corrections, and user feedback. The entrypoint owns principle reading, scope, standards, prioritization, and the shared report.

1. **Frame the completed work.** Identify the intended result, constraints, available evidence, and actual outcome. Sketch only the sequence needed to explain consequential decisions. Separate a genuinely completed slice from unfinished work; missing history is a coverage gap.
2. **Find recurring effort and effective practices.** Trace orientation, information access, editing, feedback, diagnosis, verification, coordination, and human steering. Look for repeated rediscovery, misleading examples, expensive/noisy tools, unnecessary waits or handoffs, setup/reset friction, and repeated checks without a relevant change. Retain what helped. Use recorded timings/counts when available; do not invent velocity measurements or treat a single incident as a universal rule.
3. **Explain causes.** Distinguish symptoms from causes and observations from hypotheses. Inspect the relevant code, commands, configuration, or guidance where needed; do not expand this into an automatic whole-codebase audit. Check whether a useful capability already exists but was undiscoverable or unwired before recommending a replacement.
4. **Propose durable changes.** Name the supported path and which obsolete instruction, duplicate gate, handoff, workaround, or misleading example should disappear. Prefer better APIs, examples, deterministic feedback, and runnable/inspectable/resettable behavior where they address the cause. Preserve mandatory gates and meaningful evidence; faster verification must still support its claim. Use prose for contextual judgment, not as a substitute for practical enforcement.
5. **Choose the next improvement.** Identify the owner: project code/tooling, project guidance, shared standards/skills, or coordination practice. State expected benefit, cost/risk, and what subsequent work would show if the change helped. Use a bounded experiment when the cause or remedy is uncertain. A new harness, platform, or orchestration layer needs evidence that simpler existing mechanisms are insufficient.

Return observations and candidates to the shared report. Consolidate causes also found by codebase review. End at recommendations within current authorization; do not silently rewrite shared skills or add acceptance gates. Sparse evidence supports a limited retrospective, not a fabricated account of what happened.
